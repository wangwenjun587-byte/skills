# Skill 测试维度参考手册

本文档详述 Skill Test Runner 的 7 个测试维度，包含评分标准、测试用例模板和常见问题示例。  
Claude 在执行测试时应加载此文件作为参考。

---

## 1. 输出质量（Output Quality）

**目标**：评估 Skill 的输出是否达到预期的格式、完整性和专业度。

### 评分标准

| 分数 | 含义 |
|------|------|
| 5 | 格式完全正确，内容完整，表达专业，无冗余 |
| 4 | 格式基本正确，内容完整，有少量冗余或表达瑕疵 |
| 3 | 格式部分正确，关键内容存在但不完整 |
| 2 | 格式混乱或关键内容缺失 |
| 1 | 输出无法使用，格式完全错误或内容严重缺失 |

### 测试用例模板

```
测试输入：[使用 Skill 的典型 Prompt]
期望格式：[Markdown表格 / JSON / 纯文本 / 代码块]
期望内容：[必须包含的关键信息]
检查项：
  □ 输出格式是否符合 Skill 的声明
  □ 内容是否完整（无截断、无省略）
  □ 表达是否专业清晰
  □ 是否有不必要的废话或重复
  □ 特殊字符/编码是否正常
```

### 常见问题
- **截断**：输出在 token 限制处突然中断
- **格式漂移**：Skill 声明输出 JSON 但实际输出 Markdown
- **冗余**：重复解释同一件事 2-3 次
- **省略号滥用**：用 `...` 代替实际内容

## 2. 稳定性（Stability）

**目标**：评估相同输入多次运行结论是否一致。

### 评分标准

| 分数 | 含义 |
|------|------|
| 5 | 3次运行结果完全一致（允许措辞小差异） |
| 4 | 核心结论一致，格式有轻微差异 |
| 3 | 2/3次一致，1次有偏差 |
| 2 | 结果随机，无规律 |
| 1 | 每次结果都不同，完全不可预测 |

### 测试方法
1. 使用**完全相同的 Prompt** 运行 Skill 3 次（清空上下文后）
2. 对比：关键结论、核心数字、输出格式
3. 记录差异点

### 关注指标
- **关键事实一致性**：版本号、命令、参数是否每次相同
- **格式稳定性**：是否每次都选择同样的输出结构
- **步骤完整性**：是否每次都包含相同数量的步骤

## 3. 幻觉检测（Hallucination Detection）

**目标**：检测 Skill 是否产生无法验证或明显错误的信息。

### 评分标准

| 分数 | 含义 |
|------|------|
| 5 | 所有事实均可验证，无捏造内容 |
| 4 | 99% 事实准确，有 1-2 处模糊但可容忍 |
| 3 | 有 2-3 处无法核实的声明 |
| 2 | 多处明显错误或捏造的 API/函数/链接 |
| 1 | 大量虚假信息，核心内容不可信 |

### 高风险幻觉类型

```
🔴 高风险：
  - 捏造的 npm/pip 包名（实际不存在）
  - 错误的函数签名或 API 路径
  - 编造的版本号（如声明某库版本为 x.y.z 但实际没有）
  - 虚假的文件路径或配置键名

🟡 中风险：
  - 过时的文档（API 已废弃但仍推荐使用）
  - 模糊的归因（"据研究表明"但无来源）
  - 近似正确但有关键错误的代码

🟢 低风险（可接受）：
  - 语法糖的轻微差异
  - 风格性建议
```

### 验证方法
- 代码类：在实际环境中运行代码，检查是否报错
- 文档类：用搜索引擎或官方文档核实关键声明
- 命令类：在终端中执行，观察是否报"命令不存在"

## 4. Prompt 遵循（Prompt Following）

**目标**：评估 Skill 是否严格按照用户的指令执行，无遗漏、无越权。

### 评分标准

| 分数 | 含义 |
|------|------|
| 5 | 精确执行所有指令，包括正向和负向约束 |
| 4 | 执行了全部主要指令，忽略了 1 个次要约束 |
| 3 | 执行了主要指令，遗漏了 2-3 个约束 |
| 2 | 部分执行，明显忽略了核心约束 |
| 1 | 几乎没有遵循指令，自行发挥 |

### 测试 Prompt 设计原则

```markdown
有效测试 Prompt 的特征：
  1. 包含明确的正向要求（"必须包含X"）
  2. 包含明确的负向约束（"不要使用Y"，"禁止Z"）
  3. 包含格式约束（"只输出JSON"，"不超过100字"）
  4. 包含语言约束（"只用中文回答"）
  5. 包含顺序约束（"先做A，再做B"）

示例测试 Prompt：
  "帮我写一个Python函数，只使用标准库，不要使用第三方包，
   函数名必须是 process_data，输入为列表，输出为字典，
   不要添加注释，只返回代码，不超过20行"
```

### 检查维度
- [ ] 功能需求是否全部实现
- [ ] 禁止项是否全部规避
- [ ] 格式是否符合要求
- [ ] 没有超出要求范围的额外输出

## 5. Tool 调用（Tool Call）

**目标**：评估 Skill 的工具选择、参数填写和调用策略是否正确高效。

### 评分标准

| 分数 | 含义 |
|------|------|
| 5 | 工具选择最优，参数精确，调用序列合理，无冗余 |
| 4 | 工具选择正确，有 1-2 处轻微冗余 |
| 3 | 工具选择基本正确，但有非最优选择或参数错误 |
| 2 | 多次选错工具或参数错误导致返工 |
| 1 | 工具使用混乱，无法完成任务 |

### 评估维度

```
工具选择评估：
  - 是否选择了完成任务的最少工具组合？
  - 是否有更合适的工具被忽略？
  - 是否重复调用了可以一次完成的工具？

参数质量评估：
  - 必填参数是否全部正确填写？
  - 可选参数是否合理使用？
  - 文件路径是否使用绝对路径？

调用序列评估：
  - 是否在写之前先读（Read before Write）？
  - 是否在搜后才取具体内容（Search then Fetch）？
  - 依赖关系是否正确处理（串行 vs 并行）？

错误恢复评估：
  - 工具报错后是否有合理重试或降级策略？
  - 是否向用户清晰报告了工具调用失败？
```

## 6. 上下文记忆（Context Memory）

**目标**：评估 Skill 在多轮对话中是否正确保持和利用上下文信息。

### 评分标准

| 分数 | 含义 |
|------|------|
| 5 | 完整记住并正确使用所有先前信息 |
| 4 | 记住了大部分信息，有 1 处轻微遗忘 |
| 3 | 记住核心信息，遗忘了次要细节 |
| 2 | 多处关键信息遗忘，需要用户重复说明 |
| 1 | 几乎没有跨轮次记忆，每轮都像全新开始 |

### 测试流程设计

```
轮次1：引入关键约束/变量
  示例："我们项目使用 Python 3.11，包管理器是 poetry，
        代码风格遵循 PEP 8，所有函数都需要类型注解"

轮次2：测试基础记忆
  示例："帮我写一个读取 CSV 的函数"
  验证：是否使用 Python 3.11 兼容语法？是否有类型注解？

轮次3：引入新变量并测试叠加记忆
  示例："这个函数需要处理大文件，用生成器实现"
  验证：是否保留了之前的类型注解要求？

轮次4+：长程记忆测试
  示例："把前面写的几个函数整合成一个模块"
  验证：是否能正确引用所有之前的函数和约束？
```

### 记忆测试关注点
- 变量名/文件名的精确记忆
- 约束条件的持久性（不随轮次增加而淡化）
- 决策的一致性（第1轮做的技术选型在后续是否被遵守）

## 7. 异常处理（Error Handling）

**目标**：评估 Skill 在面对异常输入、边界条件和错误状态时的健壮性。

### 评分标准

| 分数 | 含义 |
|------|------|
| 5 | 所有异常情况都有友好提示和降级方案 |
| 4 | 大多数异常处理良好，有 1-2 个边界未处理 |
| 3 | 常见异常处理正常，极端情况会崩溃或乱输出 |
| 2 | 经常遇到未处理异常，错误提示不友好 |
| 1 | 遇到任何异常都会失败，无有效恢复 |

### 测试用例库

```markdown
空值测试：
  - 发送空字符串 ""
  - 发送只含空格的字符串 "   "
  - 不提供必要参数

边界值测试：
  - 极长输入（10000+ 字符）
  - 极短输入（1个字符）
  - 特殊字符（<>{}|\\^~[]`）
  - Unicode 字符（中文/日文/Emoji）

语义异常测试：
  - 自相矛盾的指令："只用Python，但必须用JavaScript实现"
  - 要求不可能的任务："在不使用任何变量的情况下写冒泡排序"
  - 超出能力范围的请求

文件/资源异常测试：
  - 引用不存在的文件路径
  - 引用损坏的文件
  - 网络不可用时的网络请求

权限和安全测试：
  - 要求执行危险操作（如删除系统文件）
  - 注入类攻击（Prompt injection 测试）
```

## 综合评分计算

```
总分 = Σ(各维度分数)
最高分 = 测试维度数 × 5

等级划分：
  90-100% → 🏆 A+ 可信赖   （生产环境可放心使用）
  75-89%  → ✅ A  良好可用  （可使用，关注低分维度）
  60-74%  → ⚠️  B  需要改进  （建议改进后再大范围使用）
  40-59%  → 🚨 C  风险较高  （仅在监督下使用）
  <40%    → ❌ D  不可靠    （重构或放弃该 Skill）
```
