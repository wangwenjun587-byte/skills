# Skill 冒烟测试调度器

> **一键扫描 → 逐个执行 → 汇总报告**。不读文档猜质量，而是真跑一遍看成败。

---

## 核心思路

```
扫描本地所有 Skill
    ↓
为每个 Skill 设计一个「最简单的成功场景」
    ↓
用子 Agent 逐一执行（读 SKILL.md → 按其流程跑一遍）
    ↓
检查执行结果是否符合预期
    ↓
输出汇总报告：每个 Skill ✅/❌ + 7 维度评分 + 问题清单
```

**关键区别**：不是静态分析 SKILL.md 写得好不好，而是**实际触发 Skill 执行**，看它跑不跑得通。

---

## 执行流程

### Phase 1：扫描 & 排序

```
1. 扫描 Skill 目录：
   - 用户级：~/.workbuddy/skills/*/SKILL.md
   - 插件级：~/.workbuddy/plugins/marketplaces/cb_teams_marketplace/plugins/*/SKILL.md
   - 如用户指定路径，额外扫描指定目录
   - 排除自身（test-skill）和 skill-creator

2. 读取每个 SKILL.md 的 frontmatter（name + description）

3. 展示列表给用户确认测试范围：
   ┌────┬─────────────────────┬──────────────────────────────────┐
   │ #  │ Skill               │ 描述                              │
   ├────┼─────────────────────┼──────────────────────────────────┤
   │ 1  │ 去AI味              │ 去除 AI 写作痕迹                    │
   │ 2  │ 内容总结            │ 总结 URL 或文件内容                 │
   │ ...│                     │                                   │
   └────┴─────────────────────┴──────────────────────────────────┘

   用户选择：全部 / 指定编号 / 按关键词过滤
```

### Phase 2：为每个 Skill 设计冒烟测试

```
for each 被测 Skill:
  1. 读取 SKILL.md 全文
  2. 理解 Skill 核心能力（它做什么？输入是什么？输出是什么？）
  3. 设计一个「最小可验证执行」（冒烟测试）：
     - 输入：Skill 最典型的用户 prompt
     - 预期：什么样的输出算「成功」
     - 不需要测试所有功能，只要验证核心路径跑得通
  4. 同时设计 7 个维度的检测点（见下方维度表）
```

**冒烟测试设计原则**：
- 用**最简单的输入**触发核心功能
- 预期定义必须**可客观判断**（有输出 vs 无输出 / 格式正确 vs 错误 / 数据合理 vs 荒谬）
- 不测边缘 case，只测 happy path
- 每个 Skill 的冒烟测试执行时间应 < 60 秒

### Phase 3：逐个调度执行

```
for each 被测 Skill:

  # === 子 Agent 独立执行（避免主 Agent 上下文污染） ===
  spawn 子 Agent {
    1. 读取该 Skill 的 SKILL.md
    2. 按冒烟测试的输入执行
    3. 记录完整执行过程：
       - 调用了哪些工具？参数是什么？
       - 工具调用是否成功？有无报错？
       - 最终输出了什么？
    4. 返回执行记录 JSON
  }

  # === 主 Agent 评估 ===
  5. 根据执行记录，对 7 个维度打分
  6. 判断该 Skill 的冒烟测试结果：PASS 或 FAIL
  7. 记录问题（如有）
```

**超时处理**：子 Agent 执行超过 120 秒 → 标记 `timeout`，视为 FAIL

**跳过规则**（不测试但记录原因）：
- 需要外部账号/登录的 Skill（如 wechat-qq-sender）→ 标记 `skip: requires_auth`
- 需要付费 API 的 Skill 且无可用凭证 → 标记 `skip: no_credentials`
- 依赖特定硬件/环境的 Skill → 标记 `skip: env_missing`

### Phase 4：汇总报告

```
1. 统计整体结果：
   - 总 Skill 数 / 通过数 / 失败数 / 跳过数
   - 整体通过率

2. 输出控制台摘要表格（见下方格式）

3. 生成 HTML 报告（用 templates/test-report.html 模板）：
   - 每个一行：Skill 名 + PASS/FAIL + 7 维度分数 + 关键问题
   - 失败的 Skill 展开详细原因

4. 如果有失败的 Skill，给出修复建议（基于 SKILL.md 中的弱点）

5. 展示报告给用户
```

---

## 7 个评估维度

每个维度独立打 1-5 分，同时给出 PASS/FAIL 判定。

| # | 维度 | 核心问题 | PASS 条件 | FAIL 条件 |
|---|------|---------|----------|----------|
| 1 | **输出质量** | Skill 执行后有没有产出有用结果？ | 输出完整、可读、满足核心功能 | 无输出 / 输出乱码 / 内容完全偏离意图 |
| 2 | **稳定性** | 同样操作跑两遍结果是否一致？ | 核心结论和数据一致 | 两次结果矛盾或间歇性崩溃 |
| 3 | **幻觉检测** | 输出中有没有编造信息？ | 可验证的事实无编造 | 编造数据/URL/人名/路径 |
| 4 | **Prompt 遵循** | Skill 是否遵守自己 SKILL.md 定义的流程？ | 核心流程步骤执行正确 | 跳过关键步骤 / 做了禁止的事 |
| 5 | **Tool 调用** | 声明的工具是否正确调用？ | 工具选择合理、参数正确 | 用错工具 / 参数错误 / 不该调用时调用 |
| 6 | **上下文记忆** | 多轮执行时是否保持风格/偏好？ | 后续轮次遵循前轮偏好 | 每轮都重置，完全无记忆 |
| 7 | **异常处理** | 异常输入是否不会崩溃？ | 异常输入有友好处理 | 崩溃 / 输出垃圾 / 报错堆栈 |

### 综合判定规则

**单 Skill 通过标准**：7 维度中 ≥ 5 个 ≥ 3 分，且无任何维度 = 1 分

**总判定**：

| 状态 | 条件 |
|------|------|
| ✅ PASS | 满足通过标准 |
| ❌ FAIL | 不满足通过标准 |
| ⏭️ SKIP | 外部依赖不可用（认证/硬件/API） |
| ⏰ TIMEOUT | 执行超时 |
| 💥 ERROR | 执行过程中报错 |

## 报告格式

### 控制台摘要

```
┌──────────────────────────────────────────────────────────────┐
│              Skill 冒烟测试报告                                │
│              2026-05-22 15:30                                │
├──────────┬───────┬──────┬────────────────────────────────────┤
│ Skill    │ 状态  │ 分数 │ 关键发现                             │
├──────────┼───────┼──────┼────────────────────────────────────┤
│ 去AI味   │ ✅    │ 28   │ 改写质量高，异常处理薄弱              │
│ 内容总结 │ ✅    │ 31   │ URL/PDF 总结稳定可靠                 │
│ AI绘图   │ ❌    │ 18   │ Tool调用参数错误，多次超时             │
│ ...      │       │      │                                    │
├──────────┼───────┼──────┼────────────────────────────────────┤
│ 汇总     │ 5/8   │      │ 通过率: 62.5%                      │
└──────────┴───────┴──────┴────────────────────────────────────┘
```

### 失败 Skill 详细分析

对每个失败的 Skill，报告包含：

```
❌ AI绘图
   输出质量: 3/5  - 有图片输出但质量不稳定
   稳定性:    2/5  - 同一 prompt 两次执行结果差异大
   幻觉检测:  4/5  - 未发现编造
   Prompt遵循: 3/5 - 基本遵循流程
   Tool调用:   1/5  ⚠️ - ImageGen 参数格式错误导致多次失败
   上下文记忆: 3/5
   异常处理:   2/5  - 超时后无优雅降级

   → 修复建议：检查 ImageGen 工具的参数 schema，补充错误重试逻辑
```

### HTML 报告

用 `templates/test-report.html` 生成，包含：
- 总览仪表盘（通过率、分数分布）
- 每个 Skill 一行的状态列表
- 失败 Skill 的详细维度雷达图
- 问题清单（按 P0/P1/P2 分级）

## 按执行方式的冒烟测试模板

不同类型的 Skill 需要不同的冒烟测试设计。以下是常见类型的模板：

### 文本处理类（去AI味、内容总结、humanizer）

| 步骤 | 动作 |
|------|------|
| 输入 | 一段明确的文本（如含 AI 味的段落 / 一个 URL） |
| 执行 | 按 SKILL.md 流程处理 |
| 验证 | 是否有输出？输出是否与输入相关？格式是否正确？ |

### 数据查询类（neodata、westock）

| 步骤 | 动作 |
|------|------|
| 输入 | 标准查询（如"腾讯股价"） |
| 执行 | 调用 API/脚本 |
| 验证 | 是否返回数据？数据结构是否正确？数值是否合理（非零非负）？ |

### 图像/媒体类（AI绘图、image-gen）

| 步骤 | 动作 |
|------|------|
| 输入 | 简单 prompt（如"a red circle"） |
| 执行 | 调用图像生成工具 |
| 验证 | 是否生成了图片文件？文件大小 > 0？ |

### 文件操作类（docx、xlsx、pptx、pdf）

| 步骤 | 动作 |
|------|------|
| 输入 | 提供或创建一个测试文件 |
| 执行 | 读取/修改/生成文件 |
| 验证 | 文件是否存在？大小合理？内容可解析？ |

### 交互类（wechat-qq-sender、browser-use）

| 步骤 | 动作 |
|------|------|
| 输入 | 模拟用户操作 |
| 执行 | 尝试建立连接 |
| 验证 | 是否连接成功？（这类通常标记 SKIP：requires_auth） |

## 约束规则

1. **只测不改** — 不修改被测 Skill 的任何文件
2. **独立执行** — 每个 Skill 用独立子 Agent 执行，避免上下文污染
3. **客观判定** — PASS/FAIL 基于可观察的执行结果，不靠主观感觉
4. **快速失败** — 单 Skill 超时 120 秒即标记 TIMEOUT，继续下一个
5. **诚实标注** — SKIP 的 Skill 必须说明原因（认证/环境/凭证）
6. **可复现** — 每个冒烟测试的输入和预期都有明确记录
7. **最小侵入** — 测试不应产生副作用（不发送真实消息、不执行破坏性操作）
